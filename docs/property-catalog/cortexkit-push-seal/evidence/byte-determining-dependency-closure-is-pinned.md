# Evidence: `byte-determining-dependency-closure-is-pinned`

- Discovery lenses: dependencies, build configuration, lifecycle transitions.
- Trigger: fresh portfolio review found version-bump discipline cannot observe dependency drift when resolution is unrecorded.
- Code/config trail: `crates/cortexkit-push-seal/Cargo.toml` requires `hpke = "0.14"` and `getrandom = "0.4"` with `default-features = false` and explicit feature sets. The tracked workspace `Cargo.lock` records the resolved versions, sources, checksums, and dependency edges. The fixture test resolves each recorded version by walking those edges from this crate's own lock entry, so a second version of a name elsewhere in the workspace cannot be recorded as this crate's; the lock already holds two versions of `syn` and of `wasi`. Every Cargo build/lint/test command in `.github/workflows/ci.yml` uses `--locked`; `cargo fmt` does not resolve dependencies.
- Resolution fact: manifest requirements cannot record a closure. Exact `=` requirements were tried and rejected: they make one version the only satisfiable one, so they block entropy and crypto patch releases and turn a path consumer that needs a newer in-range patch into a resolution failure rather than an upgrade. They also leave the transitive graph floating, so they buy no reproducibility. The tracked lockfile plus `--locked` is the mechanism for this property.
- Default-CI identity: the manifest constrains direct versions and declares feature sets. The lockfile pins the workspace's resolved version-and-checksum closure, including implementation crates below the direct wrappers. Locked CI rejects resolution that would change that file.
- Negative control: in a temporary workspace copy, changing the push-seal `getrandom` requirement from `=0.4.3` to `=0.4.2` made `cargo test --locked -p cortexkit-push-seal --no-run` fail because `--locked` prevented a lockfile update. The canonical manifest and lockfile SHA-256 hashes were unchanged.
- Build-identity scope: the check records an approved identity per `(supported target, build purpose)`: enabled features, `getrandom_backend` configuration, Cargo edge set, and the full enabled transitive graph from the tracked lockfile rather than a hand-maintained package subset. Purposes include default verification, deterministic-vector generation, and entropy-failure testing.
- Competing explanation: suite-codepoint assertions might make resolution drift harmless. They cannot detect a same-codepoint serialization, key-schedule, clamping, or RNG-wrapper behavior change.
- Failure scenario: two fresh builds of one crate revision resolve different crypto closures and produce different bytes or classifications while local source and version remain unchanged.
- Timing/configuration: dependency publication between builds; workspace feature unification.
- Existing evidence: locked focused tests, workspace lint, workspace tests, and the live PostgreSQL CI command all consume the committed closure. The negative control proves the lock gate rejects manifest drift instead of silently rewriting the closure.
- Remaining gap: the lockfile and manifest do not audit target-specific activated features or entropy backends, alternate path consumers, the external opener, or identities for deterministic-vector, entropy-failure, release, and other build purposes. The broad property is not fully audited.
- Future instrumentation: record and compare `cargo metadata`, activated feature graph, target triple, build purpose, and `getrandom_backend` configuration for each additional identity before extending the audited claim.
- Investigation log: the unused direct `rand_core 0.9` requirement was removed and direct `getrandom` was added so `seal` can name `SysRng`. hpke's `getrandom` feature moved to `[dev-dependencies]`; the library reaches only `alloc`-gated HPKE entry points, so the shipped library no longer compiles hpke's own ambient-RNG selection. The `hex` dev dependency does not enter emitted bytes. Floating stable Rust was examined and excluded from this wire-identity property; absent a compiler defect, toolchain identity does not define HPKE wire bytes.
