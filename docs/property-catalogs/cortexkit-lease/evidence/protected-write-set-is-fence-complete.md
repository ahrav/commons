# `protected-write-set-is-fence-complete`

- **Discovery:** targeted consumer write-surface pass after portfolio evaluation.
- **Primary evidence:** SQLite runs `with_conn` under `PRAGMA query_only`, so an unfenced write fails `SQLITE_READONLY` (`cortexkit-store/src/lib.rs:140-160`), and `with_conn_unfenced` carries the maintenance statements that guard rejects (`:162-178`). PostgreSQL exposes enforced read-only and fenced transactions (`cortexkit-store-postgres/src/lib.rs:84-107,109-126`) plus an explicitly unfenced autocommit callback for statements a transaction block forbids (`:128-147`). Both migration implementations check the fence in the same transaction as schema SQL (`cortexkit-store/src/lib.rs:456-520`; `cortexkit-store-postgres/src/lib.rs:320-369`).
- **Discriminating fact:** each backend now rejects writes on its ordinary callback and retains exactly one named unfenced durable-write surface for statements a transaction block or a read-only guard forbids. Enforcement is connection state, not statement state, so `QueryOnlyGuard` clears the pragma even when the read scope unwinds (`cortexkit-store/src/lib.rs:233-266`); leaving it set would make the shared connection reject a fenced write the fence authorizes.
- **Existing evidence:** the [durable consumer inventory](../durable-consumer-inventory.md) records unfenced durable mutations in Magic Context that this enforcement now fails. Backend tests cover fenced writes, migrations, rollback, SQLite and PostgreSQL read-only rejection (`cortexkit-store/src/lib.rs:885-909`; `cortexkit-store-postgres/src/lib.rs:487-520`), that both unfenced callbacks reach statements a transaction rejects (`cortexkit-store/src/lib.rs:945-959`; `cortexkit-store-postgres/src/lib.rs:465-485`), and that a panicking read leaves later fenced writes authorized (`cortexkit-store/src/lib.rs:922-943`); none covers consumer completeness.
- **Failure scenario:** domain code performs a protected durable mutation through a named unfenced closure or a migration path, or reroutes a rejected `with_conn` write to `with_conn_unfenced` to restore the old behavior.
- **Timing window:** stale connection after handover.
- **Instrumentation:** authoritative inventory of durable-write sites plus at least one authoritative fence check atomically bound to each protected commit.
- **Open-question log:** an authoritative protected write-set classification remains unavailable, and the companion SQLite consumer migration is now a required upgrade rather than a deferred one. Whether maintenance statements through `with_conn_unfenced` and `with_client_unfenced` count as protected writes needs the same owner.
