# `protected-write-set-is-fence-complete`

- **Discovery:** targeted consumer write-surface pass after portfolio evaluation.
- **Primary evidence:** SQLite runs `with_conn` under `PRAGMA query_only`, so an unfenced write fails `SQLITE_READONLY` (`cortexkit-store/src/lib.rs:140-160`), and `with_conn_unfenced` carries the maintenance statements that guard rejects (`:162-178`). PostgreSQL exposes enforced read-only and fenced transactions (`cortexkit-store-postgres/src/lib.rs:84-107,109-130`) plus an explicitly unfenced autocommit callback for statements a transaction block forbids (`:132-151`). Both migration implementations check the fence in the same transaction as schema SQL (`cortexkit-store/src/lib.rs:484-555`; `cortexkit-store-postgres/src/lib.rs:349-401`).
- **Discriminating fact:** each backend now rejects writes on its ordinary callback and retains exactly one named unfenced durable-write surface for statements a transaction block or a read-only guard forbids. Two properties of that binding are not automatic. Enforcement and durability are connection state, not statement state, so `QueryOnlyGuard` clears `query_only` even when the read scope unwinds and `pin_fence_durability` re-asserts `synchronous=FULL` before each protected transaction (`cortexkit-store/src/lib.rs:240-281`); `query_only` permits lowering `synchronous` because that changes no database content. Separately, a callback holding the transaction can send `COMMIT`, after which its remaining statements commit in autocommit, so both backends verify the checked transaction is still in effect before committing (`cortexkit-store/src/lib.rs:283-294`; `cortexkit-store-postgres/src/lib.rs:193-238`).
- **Existing evidence:** the [durable consumer inventory](../durable-consumer-inventory.md) records unfenced durable mutations in Magic Context that this enforcement now fails. Backend tests cover fenced writes, migrations, rollback, SQLite and PostgreSQL read-only rejection (`cortexkit-store/src/lib.rs:920-944`; `cortexkit-store-postgres/src/lib.rs:564-597`), that both unfenced callbacks reach statements a transaction rejects (`cortexkit-store/src/lib.rs:1055-1069`; `cortexkit-store-postgres/src/lib.rs:542-562`), that a panicking read leaves later fenced writes authorized (`cortexkit-store/src/lib.rs:957-978`), that a fenced write and a migration re-pin `synchronous=FULL` after a read callback lowers it (`:980-1016`), and that a transaction-ending callback or migration is rejected on both backends (`:1018-1053`; `cortexkit-store-postgres/src/lib.rs:497-540`); none covers consumer completeness.
- **Failure scenario:** domain code performs a protected durable mutation through a named unfenced closure or a migration path, reroutes a rejected `with_conn` write to `with_conn_unfenced`, or ends the checked transaction and opens a replacement so its writes commit under no verified fence.
- **Timing window:** stale connection after handover.
- **Instrumentation:** authoritative inventory of durable-write sites plus at least one authoritative fence check atomically bound to each protected commit.
- **Open-question log:** an authoritative protected write-set classification remains unavailable, and the companion SQLite consumer migration is now a required upgrade rather than a deferred one. Whether maintenance statements through `with_conn_unfenced` and `with_client_unfenced` count as protected writes needs the same owner, as does whether the fenced callbacks should receive a capability-narrowed handle instead of one that can execute arbitrary SQL; detection cannot see a callback that opens a replacement transaction.
