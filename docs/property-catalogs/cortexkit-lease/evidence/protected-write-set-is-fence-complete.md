# `protected-write-set-is-fence-complete`

- **Discovery:** targeted consumer write-surface pass after portfolio evaluation.
- **Primary evidence:** SQLite runs `with_conn` under `PRAGMA query_only`, so an unfenced write fails `SQLITE_READONLY` (`cortexkit-store/src/lib.rs:140-164`), and `with_conn_unfenced` carries the maintenance statements that guard rejects (`:166-182`). PostgreSQL exposes enforced read-only and fenced transactions (`cortexkit-store-postgres/src/lib.rs:95-122,124-149`) plus an explicitly unfenced autocommit callback for statements a transaction block forbids (`:151-170`). Both migration implementations check the fence in the same transaction as schema SQL (`cortexkit-store/src/lib.rs:614-688`; `cortexkit-store-postgres/src/lib.rs:434-489`).
- **Discriminating fact:** each backend now rejects writes on its ordinary callback and retains exactly one named unfenced durable-write surface for statements a transaction block or a read-only guard forbids. Four properties of that binding are not automatic. A callback holding `&Connection` can replace the guard through `Connection::authorizer`, which takes `&self`, so guarded callbacks receive a `GuardedConn` that omits authorizer control, pragma writes, statement batches, and transaction control (`cortexkit-store/src/lib.rs:248-255`). Enforcement and durability are connection state, not statement state, so `QueryOnlyGuard` clears `query_only` even when the read scope unwinds and `pin_fence_durability` re-asserts `synchronous=FULL` before each protected transaction (`cortexkit-store/src/lib.rs:300-424`). `query_only` also permits pragma writes, including its own, because a pragma change writes no database content. Enumerating pragma names cannot be complete — `ignore_check_constraints` disables the fence table's constraint, names are case-insensitive, and `ATTACH` and savepoints escape by other means — so `CallbackScope` denies the capability classes instead: every pragma write, transaction control, savepoints, `ATTACH`/`DETACH`, and writes to the fence and version tables, for the callback's duration on both the read and the fenced path (`:370-399`). `pin_fence_durability` re-asserts `synchronous=FULL` and a WAL journal, since the unrestricted maintenance path can still set either (`:409-424`). A callback holding the transaction can otherwise send `COMMIT`, after which its remaining statements commit in autocommit. SQLite denies that statement before it executes, so nothing escapes. PostgreSQL has no authorizer, so it verifies after the callback that the transaction is still the checked one, still read-only, and still holding the same lease row (`cortexkit-store-postgres/src/lib.rs:211-312`); `SET TRANSACTION READ WRITE` reaches the same state without ending the transaction. That verification reports rather than repairs when the escape autocommitted first, while a mode switch that leaves the transaction open rolls back. Nothing reserves `cortexkit_lease` against callback SQL either, so the PostgreSQL check also confirms the locked row still carries the epoch the write was fenced against (`cortexkit-store-postgres/src/lib.rs:261-295`). A negative persisted epoch compares older than every positive holder epoch, so both backends reject it rather than let the comparison authorize a superseded writer; PostgreSQL adds the table constraint SQLite already had (`cortexkit-store-postgres/src/lib.rs:237-243,355-387,389-404`).
- **Existing evidence:** the [durable consumer inventory](../durable-consumer-inventory.md) records unfenced durable mutations in Magic Context that this enforcement now fails. Backend tests cover fenced writes, migrations, rollback, SQLite and PostgreSQL read-only rejection (`cortexkit-store/src/lib.rs:1053-1077`; `cortexkit-store-postgres/src/lib.rs:839-872`), that both unfenced callbacks reach statements a transaction rejects (`cortexkit-store/src/lib.rs:1339-1353`; `cortexkit-store-postgres/src/lib.rs:817-837`), that a panicking read leaves later fenced writes authorized (`cortexkit-store/src/lib.rs:1090-1111`), that a read callback is denied lowering `synchronous` and that a fenced write and a migration re-pin `FULL` after the maintenance path lowers it (`:1113-1178`), that a read callback cannot clear the guard or take an exclusive lock (`:1180-1234`), that a transaction-ending callback or migration is denied on SQLite and rejected on PostgreSQL (`:1162-1219`; `cortexkit-store-postgres/src/lib.rs:585-628`), that a read callback can neither end its transaction nor switch it to read-write (`:630-690`), that a negative epoch and a regressed positive epoch each fail closed (`:692-723,725-768`), and that a callback deleting or lowering its own lease row is rejected (`:770-815`), with the SQLite fence row denied the same damage (`cortexkit-store/src/lib.rs:1295-1337`); none covers consumer completeness.
- **Failure scenario:** domain code performs a protected durable mutation through a named unfenced closure or a migration path, reroutes a rejected `with_conn` write to `with_conn_unfenced`, ends the checked transaction and opens a replacement so its writes commit under no verified fence, or operates against a lease row whose epoch was corrupted before the non-negative constraint existed.
- **Timing window:** stale connection after handover.
- **Instrumentation:** authoritative inventory of durable-write sites plus at least one authoritative fence check atomically bound to each protected commit.
- **Open-question log:** an authoritative protected write-set classification remains unavailable, and the companion SQLite consumer migration is now a required upgrade rather than a deferred one. Whether maintenance statements through `with_conn_unfenced` and `with_client_unfenced` count as protected writes needs the same owner, as does whether the fenced callbacks should receive a capability-narrowed handle instead of one that can execute arbitrary SQL; detection cannot see a callback that opens a replacement transaction.
